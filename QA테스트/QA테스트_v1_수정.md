# Travel Briefing MCP QA 테스트 v1 수정 내역

> 수정·검증일: 2026-07-15 (KST)  
> 기준 문서: `QA테스트_v1_리뷰.md`  
> 범위: 리뷰에서 분류한 우선순위 1~7 및 함께 확인된 검색·도구 설명 문제

## 1. 수정 결과 요약

리뷰에서 확인한 우선순위 문제를 모두 수정했다. 네이버 검색 결과는 이제 서로 다른 게시물 수로만 명소 언급을 집계하며, 일정 생성기는 음식 시간대·구역·종일 일정 제약을 반영한다. 도시명은 내부 키뿐 아니라 한국어명과 현지어명도 처리하고, 운영 상태가 오래된 큐레이션 데이터도 공식 안내를 기준으로 갱신했다.

자동 테스트는 기존 PlayMCP 검사 5건과 새 회귀 테스트 12건, 총 17건이 통과했다.

## 2. 우선순위별 수정 사항

### 우선순위 1 — 블로그 언급 수 과대 계산

수정 전:

- 한 게시물 안에서 제목·본문과 여러 자동 별칭이 각각 집계됐다.
- 한 개 검색 결과만으로도 특정 명소가 여러 번 언급된 것처럼 보일 수 있었다.

수정 후:

- 명소 하나는 검색 결과 한 건에서 최대 1회만 집계한다.
- 점수는 해당 명소를 언급한 서로 다른 검색 결과 수가 된다.
- 일반적인 첫 단어·첫 두 단어 자동 매칭을 제거했다.
- 기요미즈데라·후시미이나리·킨카쿠지 등 필요한 표현은 `aliases`로 명시했다.
- “최근 인기”로 단정하지 않고 “서로 다른 검색 결과에서 반복 언급”으로 표현을 수정했다.

관련 파일: `tb_helpers.py`, `destinations_jp.json`

### 우선순위 2 — 일정 시간대·당일치기 제약

수정 전:

- 아침 시장이 저녁에 배치되거나 당일치기가 도착일·귀국일 일부 슬롯에 들어갈 수 있었다.
- 먹거리 카테고리인 야나가와 뱃놀이가 식사 장소처럼 취급됐다.
- 목적별 `sights_per_day` 값이 실제 일정 슬롯 수에 반영되지 않았다.

수정 후:

- 관광 장소와 식사 후보를 분리했다.
- 음식 후보의 `preferred_times`를 확인해 아침 시장과 야타이가 맞는 시간대에만 배치되도록 했다.
- 야나가와 뱃놀이의 카테고리를 `nature`로 바로잡았다.
- 이름에 “당일치기”가 있는 10개 장소에 `trip_scope: full_day`, `visit_min`, 첫날·마지막 날 제외 메타데이터를 추가했다.
- 자동 종일 일정은 3박 이상 여행의 중간 날짜에 최대 1회만 배치한다.
- 종일 일정은 해당 날짜를 독점하고 현지 점심 슬롯만 함께 표시한다.
- 커플·친구·가족·혼자 여행별 `sights_per_day`가 오전·오후 관광 슬롯 수를 바꾸도록 연결했다.

관련 파일: `tb_helpers.py`, `destinations_jp.json`, `config/vocab.json`의 기존 목적별 설정 사용

### 우선순위 3 — 지역 기반 동선

수정 전:

- 동일 구역은 10분, 다른 구역은 30분으로 고정해 실제 이동 시간처럼 보였다.
- 교토 외에는 `area` 정보가 거의 없어 동선 판단 근거가 부족했다.

수정 후:

- 같은 구역 장소를 우선해 연속 배치한다.
- 점심 시간에는 다른 구역의 시장을 억지로 삽입하지 않고 근처 로컬 식당 슬롯을 남긴다.
- 이동 안내를 `도보 이동권` 또는 `대중교통 이동 필요`로 바꿔 확인되지 않은 분 단위 시간을 제거했다.
- 기존 교토 외에 도쿄·후쿠오카 주요 장소의 `area`를 추가했다.

관련 파일: `tb_helpers.py`, `destinations_jp.json`

### 우선순위 4 — 네이버 워밍 캐시 불일치

수정 전:

- 워밍은 `display=5`, 일정 추천은 `display=10`을 사용해 서로 다른 캐시 키가 생성됐다.

수정 후:

- `config/api.json`의 `naver_blog_display` 하나로 결과 수를 관리한다.
- API 기본값, 스케줄 워밍, 일정 추천이 모두 같은 설정값 10을 사용한다.

관련 파일: `config/api.json`, `tb_config.py`, `tb_api.py`, `tb_scheduler.py`, `travel_briefing_mcp.py`

### 우선순위 5 — 도시 입력값 정규화

수정 전:

- `kyoto`는 처리하지만 `교토`나 `京都`는 도시별 결과 없이 조용히 실패할 수 있었다.
- 일본 외 국가에서 도시를 지정해도 전체 도시 가이드가 반환됐다.

수정 후:

- 내부 키, 한국어명, 현지어명, 선택적 별칭을 내부 도시 키로 변환한다.
- `교토`, `京都`, `kyoto`가 모두 `kyoto`로 처리된다.
- 알 수 없는 도시에는 입력값과 지원 도시 키를 포함한 오류를 반환한다.
- 일본 외 국가도 지정한 도시만 도시 가이드에 표시한다.

관련 파일: `tb_helpers.py`, `travel_briefing_mcp.py`

### 우선순위 6 — 큐레이션 상태와 사실 정보

수정 후:

- 홋카이도청 구본청사(붉은벽돌)를 `active`로 변경하고 확인일을 2026-07-15로 갱신했다.
- 슈리성은 현재 `under_renovation`을 유지하고 정전 일반 공개 예정일 `2026-11-23`을 기록했다.
- 하코네 설명의 부정확한 “신칸센 40분” 표현을 “도쿄에서 약 1시간 30분”으로 수정했다.
- 공식 운영을 확인한 쿠라마 온천의 개별 확인일을 갱신했다.

관련 파일: `destinations_jp.json`

공식 확인 근거는 `QA테스트_v1_리뷰.md`의 “운영 상태 확인 근거”에 기록했다.

### 우선순위 7 — 회귀 테스트

`test_curation_logic.py`를 추가해 다음을 자동 검증한다.

- 명소 언급의 게시물 단위 집계
- 일반 도시명으로 특정 명소가 오탐되지 않는지
- 한국어·현지어 도시명 변환
- 일본 외 국가의 도시 선택 반영
- 당일치기의 중간 날짜 배치와 단기 일정 제외
- 음식 시간대와 구역 제약
- 목적별 관광 슬롯 수
- 큐레이션 필수 필드·상태·당일치기 메타데이터
- 홋카이도청 구본청사와 슈리성 상태
- 네이버 display 설정 공유
- 네이버 결과의 날짜 보존과 중복 링크 제거

## 3. 네이버 검색 결과 추가 개선

- 동일 링크 검색 결과를 한 번만 남긴다.
- `postdate`를 보존해 후기 날짜를 결과에 표시할 수 있게 했다.
- 제목과 설명의 HTML 태그·엔티티·일부 장식 문자를 정리한다.
- 검색 결과 10건 전체를 언급 집계에 사용하되 응답에는 상위 5건을 표시한다.
- 후기 설명 노출 길이를 60자에서 110자로 늘려 호스트 LLM이 참고할 문맥을 보강했다.
- `sort=sim`은 최신순이 아니라 관련도순이므로 인기나 최신성을 보장하는 신호로 사용하지 않는다.

관련 파일: `tb_api.py`, `tb_helpers.py`

## 4. 도구 설명 정합성

- 일본 도시 요청만 스팟 단위 일자별 코스를 제공한다는 점을 `recommend_itinerary` 설명에 명시했다.
- 일본 외 국가는 도시 특징과 실제 후기 중심이라는 현재 지원 범위를 표시했다.

관련 파일: `travel_briefing_mcp.py`

## 6. 남은 제한 사항

- 분 단위 실제 이동 시간은 경로 API 없이 계산하지 않는다. 현재는 구역 기반의 정성적 안내다.
- `area` 데이터는 우선 재현 사례가 있던 교토·도쿄·후쿠오카부터 적용했다. 나머지 일본 도시는 순차 보강이 필요하다.
- 네이버 `sort=sim` 결과는 관련 후기 신호이며 검증된 방문객 수나 최신 인기 순위가 아니다.
- 자동 당일치기는 3박 이상에서 최대 1회라는 보수적 규칙을 사용한다. 사용자가 당일치기를 명시적으로 원하거나 원하지 않는 의도까지 직접 받는 입력값은 아직 없다.
- Docker 빌드와 동시 요청 부하 테스트는 이번 수정 범위에서 실행하지 않았다. 전역 4개 워커를 사용하는 일정 추천은 별도 부하 검증이 필요하다.
