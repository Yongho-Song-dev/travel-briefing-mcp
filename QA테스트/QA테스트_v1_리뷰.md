# Travel Briefing MCP QA 테스트 v1 리뷰

> 검토일: 2026-07-15 (KST)  
> 검토 범위: 큐레이션 데이터, 네이버 블로그 검색·정제·언급 집계, 일정 생성, MCP 전송 및 도구 호출  
> 기준 브랜치: `prod`

## 1. 종합 결과

MCP 서버의 기본 동작과 외부 API 연동은 정상이다. 실제 Streamable HTTP 서버 기동, MCP 초기화, 7개 도구 목록 조회, `get_destinations` 호출에 성공했다. 실제 네이버 검색은 10건을 정상 반환했고, 교토 일정 추천 1회는 외부 API를 포함해 약 256ms에 응답했다.

다만 새로 추가한 블로그 언급 기반 명소 정렬과 일자별 일정 생성에는 추천 정확도를 해칠 수 있는 문제가 확인됐다. 정적 큐레이션과 네이버 검색 신호를 결합하는 방향은 타당하지만, 네이버 결과는 검증된 인기도가 아닌 보조 신호로 다루고 일정 엔진에는 시간대·지역·당일치기 제약을 추가해야 한다.

## 2. 확인된 문제

### 우선순위 1 — 블로그 언급 수 과대 계산

- 명소명 전체, 앞 두 단어, 첫 단어, 공백 제거형을 모두 센 뒤 합산한다.
- 제목과 본문에 같은 명소가 있으면 다시 중복 집계한다.
- 테스트에서 게시물 한 건의 `후시미 이나리 대사`가 6회 언급으로 계산됐다.
- 게시물 한 건만으로도 “자주 등장한 명소”가 될 수 있어 동적 순위의 신뢰도가 낮다.

권장 조치:

- 한 게시물에서 명소당 최대 1회만 집계한다.
- 명소를 언급한 서로 다른 게시물 수를 점수로 사용한다.
- 일반적인 첫 단어 자동 별칭을 제거하고 큐레이션의 명시적 `aliases`를 사용한다.

### 우선순위 2 — 일정 시간대·당일치기 제약 부족

재현된 예:

- 아침 시장인 츠키지가 도착일 저녁에 배치됨
- 하코네·유후인 당일치기가 귀국일 오전에 배치됨
- 교토 쿠라마 온천 다음에 후시미 이나리가 배치됨
- 가족여행 일정이 다자이후→야나가와→하카타로 구성됨

권장 조치:

- `preferred_time`, `trip_scope`, `visit_min`, `avoid_first_day`, `avoid_last_day` 메타데이터를 사용한다.
- 종일 일정은 첫날·마지막 날에서 제외하고 중간 날짜 하나를 독점하도록 한다.
- 목적별 `sights_per_day`가 실제 관광 슬롯 수에 반영되도록 한다.

### 우선순위 3 — 지역 기반 동선 묶음 부족

- 이동 시간은 동일 구역 10분, 다른 구역 30분으로 고정돼 있다.
- `area` 데이터는 교토에만 있어 나머지 도시에는 이동 힌트가 없다.
- 다른 구역이라고 모두 30분인 것은 아니므로 실제 시간처럼 단정하면 위험하다.

권장 조치:

- 같은 `area`의 장소를 연속 배치한다.
- 경로 API가 없는 상태에서는 이동 시간을 확정하지 않고 `도보 이동권`, `대중교통 이동 필요` 수준으로 안내한다.

### 우선순위 4 — 네이버 워밍 캐시 불일치

- 일정 추천은 `display=10`, 워밍 스케줄러는 `display=5`를 사용한다.
- 캐시 키에 display 값이 포함되므로 워밍 결과를 일정 추천이 재사용하지 못한다.

권장 조치:

- 네이버 결과 수를 단일 설정으로 관리해 API, 스케줄러, 일정 추천이 같은 값을 사용하도록 한다.

### 우선순위 5 — 도시 입력값 정규화 부족

- `city="kyoto"`는 정상이나 `city="교토"`는 오류 없이 도시 일정이 사라진다.
- 도시 키 스키마가 자유 문자열이라 한국어·현지어가 전달될 가능성이 높다.

권장 조치:

- 내부 키, 한국어명, 현지어명을 동일한 도시 키로 정규화한다.
- 인식하지 못한 도시는 지원 키와 함께 명시적 오류를 반환한다.

### 우선순위 6 — 큐레이션 상태 데이터 노후화

- 홋카이도청 구본청사(붉은벽돌)는 2025-07-25 재개관했지만 `under_renovation`으로 남아 일정에서 제외된다.
- 슈리성 정전은 2026-11-23 일반 공개 예정이므로 현재 공사 중 표시는 유효하다.
- 모든 장소의 `verified_date`가 같아 실제 개별 확인 시점을 추적하기 어렵다.

권장 조치:

- 홋카이도청 구본청사를 `active`로 갱신한다.
- 슈리성에 예정 공개일을 별도 메타데이터로 기록한다.
- 상태가 바뀔 수 있는 장소는 개별 확인일을 갱신한다.

### 우선순위 7 — 새 로직 전용 회귀 테스트 부재

현재 자동 테스트는 PlayMCP 메타데이터와 전송 설정을 주로 검증한다. 다음 항목의 테스트가 필요하다.

- 명소 언급 수가 게시물 단위로 집계되는지
- 일반 도시명만으로 특정 명소가 오탐되지 않는지
- 당일치기가 첫날·귀국일에 배치되지 않는지
- 선호 시간대가 반영되는지
- 도시 한국어명·현지어명이 내부 키로 변환되는지
- 큐레이션 JSON 필수 필드와 상태 값이 유효한지
- 워밍과 실제 검색의 display 값이 일치하는지

## 3. 추가 품질 의견

- 네이버 검색은 `sort=sim`이므로 “최근 인기”보다 “쿼리 관련도가 높은 결과”에 가깝다.
- 검색 결과의 `postdate`를 보존하면 후기 날짜와 출처를 응답에 표시할 수 있다.
- `food` 카테고리를 무조건 식사 슬롯으로 사용하면 야나가와 뱃놀이 같은 체험이 식사로 배치된다. 콘텐츠 카테고리와 일정 역할을 분리해야 한다.
- 일본 외 국가에는 스팟 큐레이션이 없으므로 `city`를 지정해도 실제 일자별 코스가 생성되지 않는다. 도구 설명과 실제 지원 범위를 일치시킬 필요가 있다.
- 전역 스레드 풀 워커가 4개이고 일정 추천 한 건이 4개 작업을 동시에 사용하므로 동시 요청 부하 테스트가 필요하다.

## 6. 권장 구조

```text
검증된 큐레이션 = 추천 후보와 안전장치
네이버 검색 = 관련 후기와 시점별 참고 신호
일정 엔진 = 시간대·지역·당일치기 제약 적용
호스트 LLM = 설명과 최종 개인화
```

이 구조를 유지하면서 위 7개 우선순위를 해결하면, 단순 관광지 나열이 아니라 검증된 큐레이션과 실제 후기 신호를 결합한 여행 일정 MCP라는 차별점이 분명해진다.
