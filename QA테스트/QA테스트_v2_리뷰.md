# Travel Briefing MCP QA 테스트 v2 리뷰 — 카카오 LLM 응답 품질 개선

> 문서 작성일: 2026-07-20 (KST)  
> 실제 재현일: 2026-07-17 (KST)  
> 검토 범위: 동일 MCP를 사용하는 Claude·카카오 LLM의 도구 선택, 원문 보존, 일정 자연스러움, 사실성, 출처 및 지도 링크  
> 테스트 질문: `도쿄로 2박3일 커플 여행 가려하는데 여행 전 준비사항들과 여행일정을 자세히 짜줘`  
> 성격: 피드백 및 개선 제안 문서. 이 문서 작성 과정에서 구현 코드는 수정하지 않음

## 1. 종합 결론

카카오 LLM은 복합 일정 질문에 `recommend_itinerary`를 호출해 도구 선택과 파라미터 전달은 Claude보다 정확했다. 반면 MCP가 반환한 출발 전 필수 정보, 날짜 추정 경고, Google Maps 링크, 체류시간, 이동 힌트, 추천 이유, 후기 출처를 최종 답변에서 상당 부분 삭제했다. 결과적으로 큐레이션 데이터에는 충실하지만 사용자가 요구한 “여행 전 준비사항”과 “자세한 일정”은 충분히 전달하지 못했다.

Claude는 `get_trip_briefing`, `get_exchange_rate`만 호출하고 일정 도구는 사용하지 않았다. 답변은 자연스럽지만 일정, 항공권·숙박 가격, 예산을 자체 지식으로 생성했다. 사용자가 예산을 입력하지 않았는데 “1인당 70만원”과 가격 범위를 제시한 것은 MCP 근거가 없는 추정이다.

권장 방향은 다음과 같다.

```text
카카오의 정확한 도구 선택
        +
MCP 서버가 완성하는 사용자용 최종 답변
        +
호스트 LLM은 사실·장소·링크를 바꾸지 않고 말투만 최소 조정
```

현재 단계에서는 MCP 내부에 1B 모델을 먼저 추가하기보다 결정론적인 일정·검증 로직과 최종 렌더러를 강화하는 편이 효과와 안정성이 높다.

## 2. 비교 대상 결과

### 2.1 Claude

호출 도구:

- `get_trip_briefing`
- `get_exchange_rate`

특징:

- 비자, 전압, 시차, 환율, 긴급 연락처, Visit Japan Web 등을 자연스럽게 설명했다.
- 신주쿠·시부야, 하라주쿠, 아사쿠사를 날짜별로 묶어 읽기 쉬운 일정을 생성했다.
- 일정 전용 도구를 호출하지 않아 일정 장소와 구성은 MCP 큐레이션이 아닌 Claude의 자체 지식에 의존했다.
- 사용자 입력에 없는 예산과 실시간 확인되지 않은 항공권·숙박 가격을 생성했다.
- 정확한 여행 날짜가 없는데 스미다가와 불꽃축제를 여행 일정 후보로 제시했다.

### 2.2 카카오 LLM

호출 도구:

- `recommend_itinerary`

전달된 것으로 판단되는 주요 파라미터:

```json
{
  "country": "JP",
  "city": "tokyo",
  "nights": 2,
  "purpose": "couple"
}
```

특징:

- 질문 의도에 맞는 종합 일정 도구를 정확히 선택했다.
- 큐레이션 장소와 네이버 후기 언급 신호를 일정에 사용했다.
- MCP 원문을 크게 압축하면서 여행 전 필수 정보와 근거 링크를 삭제했다.
- 문장 연결 없이 슬롯을 나열해 최종 답변이 일정 데이터 표처럼 보였다.
- `현지 로컬 맛집` 같은 미완성 플레이스홀더가 그대로 노출됐다.

## 3. 현재 MCP 원문 재현 결과

현재 작업 트리에서 다음 호출을 실제 외부 API와 함께 실행했다.

```python
recommend_itinerary(
    country="JP",
    city="tokyo",
    nights=2,
    purpose="couple",
)
```

확인된 원문 내용:

- 추정 일정: `2026-08-16 ~ 2026-08-18`
- 정확한 날짜가 필요하다는 경고 포함
- 비자: 90일 무비자 정적 폴백
- 외교부 안전 API: 타임아웃으로 조회 실패
- 환율: `JPY(100) = 약 918.36원`, 2026-07-16 고시
- 성수기·예약 시점 안내 포함
- 모든 큐레이션 장소에 Google Maps 링크 포함
- 장소별 체류시간, 구역 이동 힌트, 커플 추천 이유 포함
- 네이버 후기 5건과 제목·링크·작성일·요약 포함
- 시부야가 서로 다른 후기 3건에서 언급됐다는 집계 포함

카카오의 사용자용 답변에서 삭제된 항목:

- 정확한 날짜가 아니라 추정 날짜라는 경고
- 비자, 외교부 안전 조회 상태, 환율 기준일, 시즌 요약
- Google Maps 링크
- 장소별 예상 체류시간
- 같은 구역·다른 구역 이동 힌트
- 각 장소가 커플 여행에 적합한 구체적 이유
- 네이버 후기 제목, 링크, 작성일, 검색 쿼리
- 데이터가 참고용이라는 주의 문구

따라서 현재 카카오 결과의 정보 부족은 MCP 데이터 부재보다 호스트 LLM의 압축·재작성 영향이 크다.

## 4. 사실성 검토

### 정상 또는 근거가 있는 내용

- 한국 일반 여권 소지자는 관광 목적 일본 단기 방문 시 90일 비자 면제 대상이다.
- Visit Japan Web은 입국심사·세관신고 정보를 사전 등록하는 일본 디지털청 공식 서비스다.
- 재현 시점 환율 100엔당 약 918원은 수출입은행 2026-07-16 고시값과 일치했다.

### 주의가 필요한 내용

- 여행 날짜를 입력하지 않았는데 `2026-08-16 ~ 2026-08-18`을 확정 일정처럼 표시했다.
- 2026년 스미다가와 불꽃축제는 7월 25일인데 추정 여행일은 8월 16~18일이어서 일정과 겹치지 않는다.
- 외교부 안전 조회가 실패했는데 `🟢 안전: 조회 실패`로 표시됐다. 초록색 아이콘은 안전이 확인됐다는 인상을 준다.
- Claude가 생성한 항공권·숙박 가격과 1인 예산은 사용자가 요청하거나 MCP가 제공한 값이 아니다.

공식 확인 근거:

- 일본 단기 비자 면제: [일본 외무성](https://www.mofa.go.jp/j_info/visit/visa/short/novisa.html)
- Visit Japan Web: [일본 디지털청](https://services.digital.go.jp/visit-japan-web/)
- 2026년 스미다가와 불꽃축제 일정: [공식 사이트](https://www.sumidagawa-hanabi.com/about/index.html)

## 5. 발견된 문제와 우선순위

### P0-1 — MCP 원문 핵심 필드가 카카오 답변에서 삭제됨

사용자가 명시적으로 요청한 여행 전 준비사항과 “자세한” 일정에 필요한 필드가 최종 답변에서 빠졌다.

필수 보존 대상:

- 날짜가 추정값인지 여부
- 비자·안전·환율·시즌
- API 실패 경고
- 지도와 공식·후기 출처 링크
- 장소별 체류시간과 이동 힌트

권장 조치:

- MCP가 호스트 LLM용 재료가 아니라 그대로 표시할 수 있는 완성된 최종 마크다운을 반환한다.
- 도구 설명 첫 문장에 `Preserve dates, warnings, sources, and map URLs`를 짧게 명시한다.
- 가능하면 최종 마크다운과 함께 구조화 필드 `pretrip`, `days`, `map_url`, `sources`, `warnings`를 반환한다.

### P0-2 — 복합 질문인데 여행 전 준비가 요약 수준에 머묾

현재 `recommend_itinerary` 원문에도 비자·안전·환율·시즌만 요약된다. 사용자가 준비사항을 요청했을 때 필요한 다음 항목은 충분히 제공되지 않는다.

- 전압과 플러그
- 시차
- 긴급 연락처와 대사관
- Visit Japan Web
- 로밍·eSIM
- 여행자보험
- 여권·항공권·숙소 바우처
- D-day 체크리스트

권장 조치:

- 종합 일정 도구 하나에 전체 여행 전 준비 블록을 포함한다.
- 작은 호스트 LLM이 여러 도구를 추가 호출할 것이라고 가정하지 않는다.
- `include_pretrip: bool = True`를 기본값으로 두는 방안을 검토한다.

### P0-3 — 날짜 미입력 시 임의 날짜와 행사 불일치

현재 내부 계산에 필요한 날짜가 사용자에게 확정 일정처럼 표시된다. 이 때문에 8월 일정에 7월 행사를 추천하는 모순이 발생했다.

권장 규칙:

- 날짜 미입력: `출발일 미정 · 2박3일 기준`
- 월만 입력: `8월 여행 기준`
- 정확한 날짜 입력: 실제 출발일과 귀국일 표시
- 행사는 여행 기간과 날짜가 겹칠 때만 노출

```python
if event.start_date <= trip_end and event.end_date >= trip_start:
    show_event(event)
```

### P0-4 — 안전 API 실패를 초록색으로 표시

`조회 실패` 상태가 `🟢` 아이콘과 함께 나타나므로 신뢰성 문제가 있다.

권장 조치:

- 성공하고 경보가 없는 경우만 `🟢`를 사용한다.
- 조회 실패는 `⚪ 확인 필요` 또는 `🟡 실시간 확인 실패`로 표시한다.
- 실패 시 폴백 데이터의 기준일과 외교부 확인 링크를 함께 제공한다.

### P1-1 — 지역 동선 최적화 부족

재현된 일정:

- Day 1: 아사쿠사 → 신주쿠
- Day 2: 우에노 → 시부야 → 메이지신궁
- Day 3: 신주쿠

동쪽과 서쪽을 날짜별로 왕복한다. 장소별 `area`를 사용하지만 일자 경계를 포함한 전체 경로 최적화가 부족하다.

권장 동선 예:

- 서부권: 신주쿠 → 메이지신궁 → 하라주쿠·오모테산도 → 시부야
- 동부권: 아사쿠사 → 우에노 → 아메요코

개선 기준:

- 하루의 주 활동 권역은 1개, 최대 2개로 제한한다.
- 첫날은 숙소 또는 도착 공항 방향을 고려한다.
- 마지막 날은 출국 공항 접근성을 고려한다.
- 영업시간이 있는 신궁·공원은 쇼핑·야경보다 앞에 배치한다.

### P1-2 — 미완성 식사 플레이스홀더

`현지 로컬 맛집`은 “자세히 짜줘”라는 요청을 충족하지 못한다.

개별 가게의 폐업 위험을 피하면서 다음 수준까지 구체화할 수 있다.

- 지역: 시부야역·아사쿠사·우에노 아메요코
- 메뉴: 스시·라멘·몬자야키·텐동·소바
- 선택 기준: 예약 필요, 웨이팅, 이동 동선

예시:

> 저녁 · 시부야역 주변에서 스시 또는 야키토리 — 시부야 야경 일정 후 도보 이동 가능한 곳을 선택

### P1-3 — 네이버 후기 품질 필터 부족

실제 검색 결과에 다음 항목이 포함됐다.

- 2026년에 작성한 2008년 여행 회고
- 도쿄 질문에 포함된 하코네 여행·상품성 후기
- 여행 일정과 직접 관련성이 낮은 결과

권장 필터:

- 게시일과 본문에 나타난 실제 여행 시점을 분리한다.
- 제목·요약에서 대상 도시 일치도를 점수화한다.
- 협찬·상품·단독투어 등 광고 가능성 신호를 별도 표시한다.
- 일정 추천에는 도시 일치도가 높은 후기만 사용한다.
- 후기 언급 수는 방문객 수나 인기 순위가 아니라 검색 결과 반복 언급 신호라고 표현한다.

### P1-4 — 서버 원문에 내부 지시문 노출

현재 원문에는 다음과 같은 호스트 LLM 대상 문장이 있다.

> 위 뼈대에 식사 메뉴를 더해 안내해 주세요.

작은 LLM이 이를 수행하지 못하면 미완성 일정이 노출되고, 수행 과정에서 링크와 경고를 삭제할 수 있다.

권장 조치:

- 내부 지시문을 제거한다.
- 식사와 연결 문장까지 서버 렌더러가 완성한다.
- 호스트 LLM에 새 사실이나 장소를 생성하도록 요구하지 않는다.

### P2-1 — 응답 버전과 데이터 상태 식별 불가

운영 환경의 답변이 최신 코드인지, 플랫폼 캐시 또는 이전 배포 결과인지 사용자 답변만으로 구분하기 어렵다.

권장 메타데이터:

```text
response_version: itinerary-v2
generated_at: 2026-07-20T...
curation_reviewed_at: ...
exchange_quoted_at: ...
visa_source: live | static_fallback
alert_source: live | failed
naver_source: live | cache | failed
```

사용자에게는 핵심 기준일만 보여주고 전체 값은 구조화 결과나 디버그 로그에 보관한다.

## 7. 도구 입력 개선안

`recommend_itinerary`에 다음 입력을 검토한다.

```python
detail_level: Literal["compact", "detailed"] = "detailed"
include_pretrip: bool = True
arrival_time: Optional[str] = None
departure_time: Optional[str] = None
arrival_airport: Optional[str] = None
departure_airport: Optional[str] = None
```

적용 원칙:

- 사용자가 “자세히”라고 했는데 `detail_level`이 누락돼도 기본값으로 상세 응답을 제공한다.
- 공항과 항공 시간이 없으면 답변을 중단하지 않고 가정을 명시한다.
- 사용자에게 확인되지 않은 공항과 시간은 확정값으로 표시하지 않는다.

## 9. 1B 모델 사용에 대한 의견

1B 모델을 서버 내부에 추가하더라도 사실 선택이나 일정 설계를 맡기면 다음 위험이 생긴다.

- 지도·출처·경고 삭제
- 임의 장소와 가격 생성
- 행사 날짜와 여행 날짜 불일치
- API 실패를 정상 정보처럼 표현
- 같은 내용을 반복하거나 과도하게 축약

권장 역할:

- 이미 확정된 일정 항목 사이의 연결 문장 생성
- 존댓말·간결함·친근함 등 말투 변환
- 반복 문구 제거
- 고정된 길이 안에서 요약

금지할 역할:

- 장소 추가·삭제·교체
- 날짜 계산
- 가격·환율 생성
- 안전·비자 판단
- 출처 URL 변경

1B 모델 출력 후에도 구조화 원본과 비교해 필수 필드가 모두 보존됐는지 결정론적으로 검사해야 한다.

## 10. 자동 QA 시나리오

### 대표 프롬프트

1. `도쿄로 2박3일 커플 여행 가려는데 준비사항과 일정을 자세히 짜줘`
2. `오사카 3박4일 친구들과 여행`
3. `다낭 2박3일 여행 추천해줘`
4. `8월에 방콕 가족여행 4박5일`
5. `2026-07-25 도쿄 여행, 불꽃축제 포함해줘`
6. `예산 100만원으로 발리 혼자 4박5일`
7. `출발 날짜는 모르는데 타이베이 2박3일 코스`

### 도구 호출 검사

- 복합 일정 질문은 `recommend_itinerary`를 호출하는가
- 국가·도시·숙박 수·목적이 정확히 전달되는가
- 사용자 입력에 없는 예산·인원·공항을 생성하지 않는가
- 도시가 명시됐는데 `city` 파라미터를 누락하지 않는가

### 답변 내용 검사

- 여행 전 준비 섹션이 존재하는가
- 날짜 미입력 시 추정 또는 미정임을 명시하는가
- Google Maps 링크가 최소 1개 이상 보존되는가
- 환율·비자·안전 정보에 기준일 또는 상태가 있는가
- 외부 API 실패가 정상 상태처럼 보이지 않는가
- 여행 기간과 겹치지 않는 행사를 추천하지 않는가
- 하루 지역 간 장거리 이동이 과도하지 않은가
- `현지 로컬 맛집`만 단독으로 출력하지 않는가
- 후기 제목·작성일·링크가 보존되는가
- 사용자가 입력하지 않은 항공권·숙박 가격을 만들지 않는가

## 11. 합격 기준

| 항목 | 합격 기준 |
|---|---|
| 도구 선택 | 복합 일정 질문에서 `recommend_itinerary` 호출 |
| 파라미터 | 국가·도시·숙박·목적 100% 일치 |
| 준비사항 | 비자·전압·환율·안전·입국·통신 포함 |
| 날짜 | 미입력 날짜를 확정값처럼 표현하지 않음 |
| 행사 | 여행 기간과 교차하는 행사만 표시 |
| 지도 | 일정 장소의 Google Maps 링크 보존 |
| 출처 | 환율 기준일과 후기 링크 보존 |
| 동선 | 하루 주 활동 권역 1개, 최대 2개 |
| 식사 | 최소 지역과 대표 메뉴 제시 |
| API 실패 | 중립 아이콘과 재확인 경로 표시 |
| 환각 방지 | 입력·도구 결과에 없는 예산과 가격 생성 금지 |
| 자연스러움 | 내부 지시문이나 미완성 플레이스홀더 미노출 |

## 12. 권장 적용 순서

1. `조회 실패` 상태의 초록색 아이콘 수정
2. 날짜 미입력 표시와 행사 날짜 교차 검사
3. 여행 전 준비 전체를 `recommend_itinerary`에 포함
4. 내부 지시문 제거 및 최종 사용자용 문장 완성
5. Google Maps·출처·경고의 구조화 반환과 보존 검사
6. 일자별 권역 묶음과 운영시간 기반 순서 개선
7. 네이버 후기 도시 일치·실제 여행 시점·광고성 필터
8. 응답 버전과 데이터 상태 메타데이터 추가
9. 호스트별 골든 프롬프트 회귀 테스트
